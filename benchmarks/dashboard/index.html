Read the boundary first

Every level validates before it times: each engine's signatures are verified and its ciphertexts decrypted by every other engine, and each verifier must reject a changed signed value and a wrapped SAML forgery. An operation an engine lacks is shown as unsupported with its reason, never timed. Security defaults differ; each engine is configured for the same workload, and those settings are listed in the measurement contract.

The workloads: a SAML assertion signed with its certificate in X509Data and verified through a trusted root and an untrusted intermediate; element encryption to an RSA-OAEP recipient certificate, standalone and in place inside its document; and an XSLT-transformed reference. Shared GitHub runners are noisy. Small sample counts do not establish reliable tail latency or superiority.

Command-line process

Boundary: a fresh process per sample, including launch, key loading, file I/O and the operation. Caches are warm; processes are not. RSS covers the complete process lifetime; Valgrind allocation and heap profiles are separate runs that include native libraries and exclude stacks and non-malloc mappings. The payload cases add byte-oriented AES-256-GCM encryption and five signed document shapes with named caller-supplied keys.

Latency summary: median of three repetition percentiles. CPU: median individual sample. RSS: maximum individual sample.

Library operation

Boundary: one process per engine, operation and repetition, timing each operation inside the process through the xml-sec Rust API, the Bergshamra Rust API (built outside the product workspace) and the libxmlsec1 C API. Keys, trust anchors and settings are loaded before the first sample; three warmups precede the samples. RSS covers the whole process. Allocation counts come from separate instrumented builds and count every heap allocation in the process during one operation.

Latency summary: median of three repetition percentiles. RSS: maximum over repetitions.
